= Testing Farm Red Hat Artifact Server (Production)

This directory contains the Terragrunt configuration for deploying the standalone `redhat.artifacts.testing.farm` service in production (TFT-4797 / TFT-4588).

== Architecture & Scope

The service provides artifact serving (`https://redhat.artifacts.testing.farm/<REQUEST_ID>/`) and restricted rsync-over-SSH artifact uploads from Red Hat workers.
The architecture comprises five distinct Terragrunt units:

1. `storage/`: Dedicated S3 Files storage backend (see `terragrunt/modules/artifacts-storage/README.adoc`).
2. `zone/`: Public Route53 DNS zone for `artifacts.testing.farm` in the Fedora AWS account for external NS delegation.
3. `security-group/`: Frontend security group in the Red Hat AWS account restricting ingress to approved private networks/workers.
4. `ec2/`: Single on-demand `c6in.2xlarge` EC2 instance running the RHEL 10 bootc artifact-server image with S3 Files NFS client profile.
5. `dns/`: Route53 A record pointing `redhat.artifacts.testing.farm` directly to the EC2 instance's private IPv4 address.

NOTE: Public DNS delegation publishes zone authority but does *not* make the server Internet-facing. The intended HTTP/HTTPS and SSH audience is limited to approved Red Hat / VPN / worker paths. See <<deployment-gates>> for the outstanding corporate/VPN ingress configuration.

== Dependency Graph & Rollout Sequence

Units are provisioned in four sequential dependency groups:

```text
       ┌───────────┐         ┌───────────┐
       │  storage  │         │   zone    │
       └─────┬─────┘         └─────┬─────┘
             │                     │
             ▼                     │
       ┌───────────┐               │
       │ sec-group │               │
       └─────┬─────┘               │
             │                     │
             ▼                     │
       ┌───────────┐               │
       │    ec2    │               │
       └─────┬─────┘               │
             │                     │
             └──────────┬──────────┘
                        ▼
                  ┌───────────┐
                  │    dns    │
                  └───────────┘
```

1. *Storage & Zone*: Provision S3 bucket, S3 Files filesystem/mount target, and create the Route53 child zone `artifacts.testing.farm`.
2. *Security Group*: Provision frontend SG with worker access (`sg-0cb20f3b88c57fa30`) and the approved corporate/VPN rules required by <<deployment-gates>>.
3. *EC2*: Launch on-demand `c6in.2xlarge` in the storage mount-target subnet with attached instance profile and both security groups.
4. *DNS*: Provision A record `redhat.artifacts.testing.farm` -> EC2 `private_ip`.
5. *Parent Delegation*: Hand off the child zone nameservers (`route53_zone_name_servers["artifacts.testing.farm"]`) to the parent domain owner for public NS delegation.

== DNS Design Rationale (A Record vs CNAME)

The stack intentionally uses a Route53 `A` record referencing the EC2 `private_ip` rather than a `CNAME` pointing to AWS EC2 private DNS.
VPN and corporate Red Hat clients cannot be assumed to resolve Amazon-internal VPC hostnames. A direct `A` record ensures consistent resolution across internal networks without additional DNS forwarders.

== Certificate Management & Renewal

TFT-4795 supplies nginx and these file-loading paths; TFT-4797 owns arranging and renewing the real certificate. The baked self-signed certificate/key is diagnostic-only. Issuance remains with the approved internal CA, not an implicitly selected Let's Encrypt flow.

1. Obtain a certificate for SAN `redhat.artifacts.testing.farm`, its intermediate chain and the matching private key from the approved issuer. Keep the trust roots separate from the served leaf/intermediate chain.
2. Verify administrator SSH host keys independently against authenticated EC2 console output. Use `cloud-user`, a dedicated verified known-hosts file and `StrictHostKeyChecking=yes`. A ProxyJump may route SSH through an approved worker; keep the admin identity local and agent forwarding disabled.
3. Transfer the leaf/intermediate chain and private key directly to a root-owned `0700` staging directory on the server over that verified channel. Staged private-key files must be `0600`; do not leave them on the jump worker or in uploaded logs.
4. Check the SAN, validity, chain against the approved CA, and matching certificate/key public-key fingerprints before installation. Retain the previous pair in a root-only rollback directory.
5. Install the served chain at `/etc/pki/nginx/artifacts.crt` (`root:root`, `0644`) and private key at `/etc/pki/nginx/artifacts.key` (`root:root`, `0600`). Restore SELinux contexts with `sudo -n restorecon` on both paths. Complete both replacements before validation/reload; restore both old files if validation fails.
6. Run `sudo -n nginx -t`, then `sudo -n systemctl reload nginx`. Verify the hostname from an approved client with the approved CA and normal hostname validation. Do not disable TLS verification or trust the baked test certificate as production issuance.
7. Remove staged copies after success and track expiry/renewal ownership operationally. Renewal is operator-driven: repeat the same validation/install/reload procedure. This MR does not install an automatic renewal job or claim certificate monitoring is already deployed.

== Validation & Lifecheck

Verification is on-demand via pytest under `tests/artifacts/`. The runner needs direct HTTP/HTTPS reachability to the private service as well as SSH routing, rsync, the approved CA bundle, separate admin/upload identities, verified host keys and read-only `s3:GetObject` permission for the owned probe objects. SSH ProxyJump alone does not route Python's HTTPS requests. Keep privileged private keys local; do not copy them to a production worker just to run the suite.

Supply these inputs from the deployed storage outputs and the approved access handoff (not guessed values):

`ARTIFACTS_HOST` and `ARTIFACTS_PRIVATE_IP`
`ARTIFACTS_ADMIN_USER=cloud-user` and `ARTIFACTS_ADMIN_KEY`
`ARTIFACTS_UPLOAD_USER=artifacts` and `ARTIFACTS_UPLOAD_KEY`
`ARTIFACTS_KNOWN_HOSTS` and `ARTIFACTS_CA_CERT`
`ARTIFACTS_FILESYSTEM_ID` and `ARTIFACTS_MOUNT_TARGET_IP`
`ARTIFACTS_S3_BUCKET` and optional `ARTIFACTS_AWS_PROFILE`

The CLI exposes corresponding `--artifacts-*` options. S3 verification uses the runner's approved AWS profile/default credential chain, never image-baked credentials. `ARTIFACTS_S3_SYNC_TIMEOUT` bounds eventual readback (default 300 seconds).

[source,bash]
----
# 1. Run offline unit tests for helpers
make test/artifacts/helpers

# 2. Plan Terragrunt stack
make production/plan/artifacts-redhat

# 3. Execute live lifecheck against deployed server
make test/artifacts/lifecheck

# 4. Execute lifecheck with explicit opt-in reboot validation
make test/artifacts/lifecheck/reboot
----

The live lifecheck tests:

* DNS resolution of `redhat.artifacts.testing.farm` to private IP.
* HTTP port 80 -> HTTPS port 443 redirection.
* TLS certificate SAN, chain validity, and ciphers.
* Nginx autoindex directory listing.
* CORS headers.
* Rejection of SSH shell requests and unauthorized commands by the image's `rrsync` forced command. Transport errors, authentication failures and timeouts fail these checks.
* Actual NFSv4 mount presence at the remotely resolved canonical path (`/mnt/s3files` aliases `/var/mnt/s3files` in the image), with installed S3 Files helper and persistent fstab configuration matching the expected filesystem/IP. Local filesystems, generic NFSv3 and autofs-only entries do not pass. A runtime SOURCE of `127.0.0.1` can be legitimate for the TLS proxy; do not compare it blindly with the mount-target IP.
* Write permissions of the actual upload identity, verified by successful restricted rsync, not by `test -w` as the administrator.
* Probe upload via restricted rsync-over-SSH followed by immediate single-attempt HTTPS retrieval (recording latency without retries).
* Rejection of an rsync download of the verified probe using the upload key, confirming write-only access.
* Eventual exact probe bytes in the expected backing S3 bucket, supplementing immediate HTTPS visibility. Authorization failures fail immediately; only a missing/stale probe is retried within the synchronization deadline.
* (Opt-in) Reboot verification, waiting for a changed boot ID and expected NFS recovery before checking pre-reboot probe persistence and new uploader writes. Unexpected local errors fail immediately rather than being retried as server downtime.

Probe cleanup covers partial uploads and all later failure paths; failed cleanup fails the lifecheck rather than only warning. It removes only the run's NFS probe directories. S3 synchronization is asynchronous and a versioned bucket can retain old object versions/delete markers: record owned prefixes from the logs, wait for deletion synchronization and arrange separately approved version cleanup if complete removal is required. The suite does not grant itself bucket-wide delete privileges or silently delete S3 versions.

Offline helper tests do not prove the image's actual IAM/TLS transport or SELinux behavior. Before declaring acceptance, corroborate helper runtime state and enforcing-SELinux NFS serving, then run separately approved missing-storage/fail-closed and path-escape checks. Broader CORS GET/HEAD/OPTIONS/error and gzip checks remain required; reboot/fault tests and any worker canary each need explicit approval.

== Recovery & Troubleshooting

* *Instance replacement*: Updating the AMI or instance parameters will replace the EC2 instance. The S3 Files filesystem retains all stored artifacts; the DNS A record automatically updates to the new private IP.
* *Storage protection*: Do not destroy the `storage` module while troubleshooting compute. S3 Files synchronizes asynchronously with the backing S3 bucket.
